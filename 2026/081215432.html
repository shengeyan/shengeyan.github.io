前端权限系统设计：把后端角色摘要变成可判断的权限画像

在后台管理系统中，前端权限是一块容易做烂的地方：要么散落地在页面里判断角色名，要么把权限逻辑堆在路由守卫里。本文分享一套把后端角色摘要归一化为统一权限画像、并在路由/导航/组件三层消费的前端权限系统设计。

文档目标

本文沉淀一套前端权限系统的模型、运行时链路、鉴权策略和扩展方式。核心思路：基于后端返回的角色摘要构建前端权限画像，并在路由、导航、页面和组件层提供统一的体验级访问控制。

重申：前端权限只负责用户体验控制，真正的数据安全边界必须由后端接口校验。前端权限永远不能替代后端鉴权。

系统边界

权限系统负责：

  • 登录后加载当前用户权限画像。
  • 将后端角色摘要归一化为前端可判断的 permission grants。
  • 缓存权限画像并在登录态变化时同步。
  • 控制路由访问、菜单显隐、页面按钮显隐或禁用。
  • 支持项目、模块、组、岗位等上下文 scope 判断。

权限系统不负责：

  • 替代后端接口鉴权。
  • 在客户端保存后端私有权限规则。
  • 直接按角色名散落判断业务能力。
  • 处理所有业务数据行级安全。

PERMISSION_CATALOG 为权限点提供展示信息（key、label、module、supportedActions、description）。它主要用于角色管理、权限展示和权限池维护，不直接承担鉴权逻辑。

角色预设

权限画像加载链路

  1. 用户登录成功后，保存 token 和用户信息，并派发登录态变更事件。

  2. 受保护路由进入登录守卫，确认本地存在 access_token。

  3. 路由配置在后台布局外层挂载 PermissionProvider。

  4. PermissionProvider 初始化时先读取本地权限缓存。

  5. 随后异步调用权限摘要接口。

  6. 权限摘要接口返回角色摘要。

  7. 归一化函数将摘要转换为：

    • architectureRoles
    • projectRoles
    • permissionGrants
    • isSuperAdmin
    • loadedAt

  8. PermissionProvider 写入 localStorage 缓存并更新 React Context。

  9. 页面、导航和路由守卫通过 usePermission() 消费画像。

缓存与会话同步

权限画像缓存写入 localStorage。读取缓存时会校验缓存版本号、以及 userId、isSuperAdmin、architectureRoles、projectRoles、permissionGrants、loadedAt 等结构是否有效。

以下事件会触发同步：

  • 浏览器 storage 事件（跨标签页同步）。
  • 登录态变更自定义事件。

登出或清理登录态时，同时删除权限画像缓存。

权限判断算法

核心判断函数逻辑如下：

  1. 权限仍在加载或没有画像时返回 false。
  2. isSuperAdmin 为 true 时直接放行。
  3. 聚合 permissionGrants、T 角色 grants、P 角色 grants。
  4. 使用 permissionMatches() 判断 permission key 或同资源不同 action 是否匹配。
  5. 使用 scopeMatches() 判断 grant scope 是否覆盖当前上下文。
  6. 命中的 grants 中存在 deny 时拒绝。
  7. 否则存在 allow 时放行。

permissionMatches() 支持同资源动作匹配。例如某 grant 的资源为 permission.role 且 actions 包含 edit，可以匹配 permission.role.edit。

scopeMatches() 的设计偏向”无上下文时宽松放行”：当调用方没有传 context，非全局 scope 也可能通过匹配。因此资源级按钮或操作最好传入明确上下文。

消费方式

Hook

usePermission() 返回：

  • profile
  • loading
  • error
  • refresh
  • can(permissionKey, context?)
  • canAny(requirements, context?)
  • canAll(requirements, context?)
  • canAuthorize(permissionKey, context?)

路由守卫

路由访问权限在 APP_ROUTE_META 中声明：

路由守卫会：

  • 检查当前路由是否在当前运行环境可用。
  • 读取 route meta 的 permission。
  • 权限加载中显示权限加载态。
  • 无权限显示 forbidden 错误页。

导航显隐

路由权限会被写入 NavigationItem.permission，布局层使用 getVisibleNavItems(translatedNavItems, can) 过滤导航项。权限管理入口本身可以是隐藏分组，在账号浮层中按权限展示可进入子项。

新增权限点流程

  1. 在 PERMISSION_KEYS 中新增稳定 key。
  2. 在 PERMISSION_CATALOG 中补充展示信息。
  3. 按业务需要加入组织角色预设或项目角色预设。
  4. 如果是路由访问权限，在 APP_ROUTE_META 中配置 permission。
  5. 如果是页面操作权限，在页面中使用 usePermission()、PermissionGuard 或 Can。
  6. 如果需要资源级控制，调用时传入 PermissionCheckContext。
  7. 若缓存结构或预设语义变化较大，提升权限缓存版本号。

风险点与约束

  • 不要在页面中直接判断 roleCode、levelCode 作为业务权限依据。
  • 路由权限、菜单权限和按钮权限应引用同一套 PERMISSION_KEYS。
  • 前端权限只能提升体验，接口仍必须后端鉴权。
  • 上下文权限判断需要传 context；不传 context 可能导致 scope 判断过宽。
  • 修改权限画像结构后必须考虑缓存版本兼容。
  • isSuperAdmin 前端直接放行所有权限，应确保后端返回逻辑可靠。
