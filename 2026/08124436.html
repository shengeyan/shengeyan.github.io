国际化系统设计：用中文原文当 key 的低心智成本 i18n 方案

传统 React 国际化方案通常要求开发者手写一堆语义化 key，例如 t('dashboard.submit.button')。key 怎么起、谁维护、翻译缺失怎么办，都是心智负担。本文分享一套相反的思路：直接用中文原文作为调用入口，运行时用稳定哈希生成 key，再通过扫描脚本自动维护语言资源。适合以中文为业务团队母语的 B 端项目。

系统边界

国际化系统负责：

  • 应用语言初始化、切换和本地偏好持久化。
  • React 组件、普通工具函数、路由标题、菜单文案的翻译。
  • 组件库（如 Ant Design）语言包和日期库（dayjs）语言同步。
  • 中文词条扫描、翻译队列生成、英文翻译补齐和 key 一致性检查。

国际化系统不负责：

  • 后端返回业务数据的翻译。
  • 用户输入内容的翻译。
  • 非 UI 文案的自动语义校正。
  • 服务端多语言协商。

核心设计：中文原文即调用入口

项目没有在业务代码中手写语义化 key，而是以中文原文调用：

运行时会通过 createI18nTextKey(text, context) 生成稳定 key，再从 i18next 资源表中读取翻译。若目标语言缺失翻译，defaultValue 会回退到中文原文。

这种设计降低了业务开发心智负担，但也要求中文原文保持稳定。修改中文原文会生成新 key，旧英文翻译会在扫描时被裁剪或进入待翻译队列。

稳定 key 生成

key 生成逻辑：

  • normalizeI18nText() 将连续空白归一为单空格并去除首尾空白。
  • stableI18nHash() 使用 FNV-1a 风格哈希生成 base36 字符串。
  • createI18nTextKey() 使用 k_ 前缀拼接哈希。
  • 当传入 context 或 _context 时，哈希源为 context::normalizedText。

上下文用于区分同一中文在不同语境下的翻译，例如名词和动词同形文案。

双入口翻译 API

场景 API 说明
React 组件 useAppTranslation().tx 基于 useTranslation()，语言切换时触发组件更新。
非 React 模块、配置、工具函数 tx from translate 直接使用全局 i18next 实例。
当前语言读取 useCurrentLanguage() 返回受支持语言，异常时回退默认语言。

组件内优先使用 useAppTranslation()，否则语言切换后可能不会自然重渲染。

初始化与运行时链路

  1. 根组件渲染 AppProviders。
  2. AppProviders 使用 useTranslation() 读取当前 i18n 语言。
  3. i18n 初始化模块：
    • 注册默认语言和英文两份资源。
    • 调用 resolveInitialLanguage() 决定初始语言。
    • 设置 fallbackLng 为默认语言。
    • 关闭 React suspense。
  4. resolveInitialLanguage() 按优先级选择语言：
    • localStorage 中保存的语言偏好。
    • 浏览器语言，支持默认语言的 * 和英文 *。
    • 默认语言。
  5. 语言变化后，AppProviders 同步：
    • document.documentElement.lang。
    • 组件库 ConfigProvider.locale。
    • dayjs 全局 locale。

资源结构与当前状态

当前语言资源为扁平 JSON：

核心脚本：

  • scan：扫描中文原文，生成/裁剪 key，输出 zh.json、待翻译队列。
  • tran：将待翻译项交给大模型生成英文映射，校验占位符后写入 en.json。
  • check：对比 zh.json 与 en.json key 是否一致，可设置 --strictUntranslated 在有未翻译项时失败。

扫描

扫描脚本执行流程：

  • 默认扫描源目录下 .ts、.tsx 文件。
  • 收集 tx("中文") 或 object.tx("中文")。
  • 额外扫描配置文件中的 title、label、description 字段。
  • 生成扫描结果和扫描报告。
  • 重写 zh.json。
  • 保留仍被使用的 en.json 翻译，裁剪过期英文 key。
  • 将英文缺失项写入待翻译队列。

翻译

翻译脚本执行流程：

  • 从待翻译队列读取项。
  • 默认批量大小 50。
  • 请求大模型生成英文 JSON 映射。
  • 校验 {{placeholder}} 是否被完整保留。
  • 成功项写入 en.json，失败项留在队列。
  • 支持 primary/fallback provider。

检查

检查脚本执行流程：

  • 对比两份语言资源 key 是否一致。
  • 输出英文缺失、中文缺失、待翻译队列。
  • 默认 key 不一致时失败。

与路由和菜单的集成

路由元数据和菜单构建需要支持翻译函数注入，因此布局中的菜单、分组、隐藏菜单入口都能跟随语言切换。路由加载态会根据当前 pathname 获取 route meta，再用 tx(routeMeta.title) 显示页面标题。

与组件库和日期的集成

组件库语言包由 getAntdLocale(language) 提供给顶层 ConfigProvider；DatePicker 独立 locale 由专门的函数暴露；dayjs 通过 applyDayjsLocale(language) 同步语言。

扩展语言流程

新增语言时建议按以下步骤：

  1. 在类型定义中扩展语言枚举。
  2. 在常量中补充受支持语言列表。
  3. 在初始化模块注册新 locale JSON。
  4. 增加组件库和 DatePicker locale 映射。
  5. 增加 dayjs locale 映射并导入对应包。
  6. 扩展浏览器语言识别规则。
  7. 生成并维护新语言 JSON。

开发约束与最佳实践

  • 新增中文 UI 文案必须包裹 tx() 或通过可扫描配置字段进入扫描链路。
  • 组件内优先使用 useAppTranslation().tx。
  • 工具函数、表格配置、常量文案可使用全局 tx。
  • 插值变量使用 {{name}} 形式，并确保翻译结果保留占位符。
  • 同一中文存在多语义时使用 context。
  • 不要手改生成 key 的算法，除非同步迁移全部 locale 资源。
  • 修改大量文案后运行 scan 和 check。

风险点

  • 中文原文变更会导致 key 变化，已有英文翻译不会自动复用。
  • 动态拼接中文无法被扫描脚本识别，应改为完整句式加插值。
  • 只有特定配置文件的 title、label、description 会被扫描，新增配置文案文件需扩展扫描文件列表。
  • 前端 fallback 到中文能保证可用性，但可能掩盖英文缺失，应在发布前严格检查。
