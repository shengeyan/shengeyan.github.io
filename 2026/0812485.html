路由系统设计：React Router 元数据驱动的 SPA 路由架构

后台单页应用的路由如果散落各处，会出现”路径、菜单、标题、权限、环境可见性”五处不同步的问题。本文分享一套元数据驱动的路由设计：用一份 APP_ROUTE_META 同时驱动标题、权限、导航和环境控制，避免手写散落的菜单与守卫逻辑。

文档目标

本文沉淀一套前端路由系统的目录结构、配置模型、运行链路、守卫机制和扩展流程。基于 createBrowserRouter 构建单页应用路由，并通过路由元数据统一驱动页面标题、权限、菜单和环境可见性。

系统边界

路由系统负责：

  • 定义应用内所有页面路径。
  • 懒加载页面组件。
  • 组织受保护后台路由与公开登录路由。
  • 提供登录守卫、权限守卫、环境可见性判断、异常页和 404 处理。
  • 向菜单、页面加载态和布局提供路由元数据。

路由系统不负责：

  • 页面内部业务状态管理。
  • 后端接口权限校验。
  • 复杂业务参数校验。
  • 后端路由或部署层 rewrite 配置。

路由分层设计

路由系统分为四层：

  1. 路径常量层：ROUTES 只描述路径字符串。
  2. 页面加载层：将页面模块转为懒加载组件。
  3. 路由声明层：组织实际 React Router 树。
  4. 元数据层：为标题、导航、权限、环境控制提供统一来源。

这种分层让页面入口、导航展示和权限声明解耦，但它们必须保持同步。

路径常量

路径常量包含首页重定向、看板、项目、事项、日报、评价、权限管理、系统与账号、异常与登录等。动态路径使用 :param 形式：

业务代码生成动态链接时应优先使用路径 builder 工具，避免手写字符串。

路由元数据

APP_ROUTE_META 是路由系统的关键配置源：

字段含义：

字段 说明
path 对应 ROUTES 中的路径。
title 页面标题，也用于加载态和默认导航文案。
visibleInEnvs 限制路由在哪些运行环境可见。
permission 路由访问所需权限。
nav 是否生成菜单项以及菜单展示配置。

getRouteMeta(pathname) 会将 :param 路由编译为正则进行匹配，并按路径段数量排序，优先返回更具体的路由元数据。

导航元数据

RouteNavigationMeta 支持 key、label、iconKey、hidden、defaultPath、activePaths、parentKey、order、description 等字段。

导航树由 buildNavigationFromRouteMeta(APP_ROUTE_META, tx) 自动生成。路由的 nav.parentKey 指向分组或父项后，会被挂入树结构，并按 order 排序。

路由配置树

主结构：

  1. / 重定向到默认看板。
  2. 后台受保护路由：
    • 外层登录守卫。
    • 中层权限 Provider。
    • 内层布局。
    • 子路由通过快捷函数或显式对象声明。
  3. /login 公开访问。
  4. 顶层 * 交给未知路径处理。

后台子路由统一进入布局的 <Outlet />，布局内部再包一层错误边界和页面动效容器。

页面懒加载

用 React lazy() 加载页面模块：

页面模块通常以命名导出组件，因此懒加载时通过 .then() 映射为默认导出。

懒加载包装组件为页面提供 Suspense fallback、加载态和错误边界。

守卫机制

登录守卫

使用 isAuthenticated() 判断本地是否存在 access_token，未登录时跳转登录页并记录来源路径。

权限守卫

工作流程：

  1. 读取当前 location.pathname。
  2. 通过 getRouteMeta() 获取 route meta。
  3. 判断 visibleInEnvs 是否允许当前运行环境访问。
  4. 没有 permission 时直接放行。
  5. 权限画像加载中显示权限加载态。
  6. 调用 usePermission().can() 判断权限。
  7. 无权限显示 forbidden 错误页。

运行环境守卫

路由元数据中的 visibleInEnvs 会同时影响路由访问（不可用时展示 notFound）和导航生成（不可用时不生成菜单）。这让 dev-only 页面能在生产导航和访问层同时收敛。

未知路径

后台子路由中 * 直接展示 notFound 页面。顶层未知路径处理器会先检查登录态：未登录跳登录页，已登录跳 /404 并记录请求 URL。

布局与导航选中

布局层负责把路由状态转换成导航 UI 状态：

  • 生成带翻译文案的菜单。
  • 根据权限过滤无权限项。
  • 根据当前 pathname 查找最匹配的叶子菜单。
  • 计算默认展开的父级菜单。
  • 处理点击父菜单时跳转到默认子页面。
  • activePaths 用于让详情页或动态路由高亮列表入口。

移动端抽屉菜单和桌面侧边菜单复用同一棵导航树。

路由与权限的关系

路由访问权限声明在 APP_ROUTE_META.permission。导航项权限来自对应 route meta，因此同一个权限点同时控制：

  • 直接访问路由是否放行。
  • 菜单是否显示。
  • 账号浮层中的管理入口是否显示。

页面内部更细粒度的按钮或 Tab 权限仍由页面自己调用 usePermission() 判断。

路由与国际化的关系

路由标题、导航标签、导航分组均会在运行时通过翻译函数处理；国际化扫描脚本也支持扫描路由元数据中的 title、label、description。新增 route meta 文案后应运行国际化扫描。

新增页面路由流程

  1. 在路径常量中新增路径常量。
  2. 在页面加载层新增懒加载页面导出。
  3. 在路由配置中将页面加入后台子路由或公开路由。
  4. 在路由元数据中增加标题、权限、导航和环境信息。
  5. 如果需要菜单展示，补充 nav 元数据，不直接手写菜单项。
  6. 如果是动态路径，增加 path builder。
  7. 如果涉及新权限点，先注册权限 key。
  8. 如果新增中文文案，运行国际化扫描和检查。

维护约束与风险点

  • 路径常量、路由配置、路由元数据必须同步维护。
  • 动态详情页要配置 activePaths 或静态前缀，否则菜单高亮可能不准确。
  • visibleInEnvs 只控制前端显示和访问体验，不应替代后端能力开关。
  • 路由权限只做页面级控制，页面内部操作仍需单独鉴权。
  • 顶层 / 当前固定重定向到默认看板，如果默认页权限变化，需要同步调整重定向策略。
  • 新增配置文件中的导航文案时，若不在国际化扫描白名单内，需要扩展扫描脚本。
